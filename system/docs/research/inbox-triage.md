# Inbox triage: the repeated clusters, and what each actually needs

Read from `/api/requests` on the Spark (8,935 records fetched, **2,631 open** on 2026-11-08). The open set is not 2,631 different problems -
it is a handful of clusters, most of them generated by automation. This page answers each cluster once, with the evidence behind the answer,
so the tickets can be closed or redirected instead of worked one at a time.

## "why is the ps3 version even coming up in rotation?" - answered by the code, with the same date

`gbox/mercmode.py::replaced_editions` carries the answer in its own docstring:

> *"Catalog ids of the editions this host's preferred_editions replaced (RE5 PS3 where RE5 means Switch). The idle demo must not play them:
> 2026-11-06 it filled every MercMode pause on lilspark with RE5 PS3, which read as PS3 in the rotation."*

**So the cause was the idle demo, not the rotation itself**, and the exclusion exists. Checked on 2026-11-08: the host's
`preferred_editions` pin both `re4` and `re5` to Switch, and the scheduler reported `launching Resident Evil 4 (Switch, Mercenaries)`.

**Resolution:** the ticket describes a defect that is already fixed; it should be closed with a pointer to `replaced_editions` and the
preference pin, not investigated further.

## "Unlock on load" and "Unlock everything for favorite" - a procedure, not a patch

**Measured for RE4 (Switch), 2026-11-08:** a fresh save's main menu is `NEW GAME / LOAD / LEADERBOARDS / HELP & OPTIONS / ACHIEVEMENTS` -
**there is no EXTRAS row**, so THE MERCENARIES does not exist until the save says it does. No RAM patch, key sequence or build changes that.
Twenty rounds of failed boots on this title came from a save the game could not load, not from a missing unlock mechanism.

**Resolution for RE4 Switch:** install a save that is (a) **past the village**, so EXTRAS exists, and (b) **written from a menu**, so the
title does not auto-load into "Cancel loading?" and boot-loop. `gbox/re4_switch_save.py --save <file> --replace` does the install with a
backup and a verified copy (6 tests).

**Not claimed for RE5/RE6:** their unlock paths were built separately in this project (`gbox/re_mods`, `gbox/re_switch`); the RE4 finding is
specific to RE4 Switch and must not be generalised onto those tickets without its own measurement.

## "Character replacement readiness: <title>" - 273 tickets, one of them names a game that is not there

The example read in full (`9ae636bf9d914bef`, RE5 Gold PS3) carries `context.game_id: "0000000000000000"` and
`hermes_favorite_game: "0000000000000000"`. **That is not a catalog id** - it is a null/placeholder, so the ticket cannot name its own game
and its "persistent work" has nothing to attach to.

**Suspected defect:** the automation that files these tickets is writing a placeholder game id instead of the real one. Only one ticket was
read in full, so this needs checking on a sample before it can be called a rule - but if it holds, the fix is in the filing path, not in 273
separate investigations, and the cluster collapses to one bug.

**Next action:** read 3-5 more from this cluster and compare their `context.game_id`. If they match the placeholder, file one defect against
the ticket creator and close the cluster pointing at it.

## "Mercenaries ... rank_not_verified ..." - by design, not a defect

`gbox/mercs/round_reports.py` assigns `category = 'rank_not_verified'` when the native S-rank was not observed, and records `rank.verified:
false` with the score it did see. These are **reports**, not failures: the pipeline filed a round, said honestly that the rank was not
observed, and kept going. On 2026-11-08 the newest such tickets are **done**, not open.

**Resolution:** nothing to fix. If the operator wants ranks verified, that needs a rank reader for those titles (RE5 Switch does not expose
one today), which is a feature rather than a bug fix.

## What I could not do from here

`/api/requests/{id}` is **GET-only** in this build - there is no endpoint to comment on, re-status, or close a request. So none of the above
can be applied to the tickets programmatically by this agent; it is written here for whoever holds the ticket UI, and every claim in it is
traceable to a commit or a measurement in the plan-of-record.
