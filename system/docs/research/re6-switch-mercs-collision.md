# RE6 Switch Mercenaries stages: collision (SBC) as measured

Ticket #9359 (b8f0b661170a4b75). Source: `~/gBox_alt/switch/romfs/01002A000CD48000/nativeNXx64/arc/NX/s1200.arc .. s1209.arc`. Tables: `re6-switch-mercs-collision.json`
(same folder; grids run-length coded, see below). Read-only: no game file copied, no code under `system/gbox` and no test changed, no bot module touched,
no game session or worker job API used. Modelled on `re4-switch-mercs-collision.md` (#9342). Helper code is a throwaway script outside the repository.

## Where the collision is
Each stage archive holds exactly **two** resources whose `gbox.mt_arc` type hash is `0x51fc779f`, with the 4-byte magic `SBC\xff` after zlib inflation:
`data\stage\s120N\...\s120Nh_scr` (name as listed by `gbox.mt_arc.parse`, entry `.name`) and `...s120Nh_eff`. Both are in all ten archives
(raw bytes: `h_scr` 149,224 .. 817,894; `h_eff` 3,574,214 .. 5,930,490). The gbox repository has **no SBC parser**; the parser used here is a
throwaway script (layout below, validated against the files themselves). `gbox.mt_arc.parse` + `zlib.decompress(entry.data)` were the repository parts used.
The `Soft` archives (`s120NSoft.arc`, `s121NSoft.arc`) hold the NAV mesh (`NAV` magic, 67,009 bytes compressed, 325,717 inflated, identical size for s1203 and s1213), **not parsed here**: its file
layout is a packed stream, not the RAM layout in `re6_switch.py` (not determined; a parser built from the Ghidra writer's order would settle it).

**Which resource is the collision the player walks on is not determined.** Measured only: `h_eff` carries 3.4 to 30 times as many triangles as `h_scr` (e.g. s1203: 53,460 vs 1,897) and every RAM bonus
position of the ten stages lies over a floor triangle of `h_eff` (table below), while `h_scr` misses one or two in s1203, s1205, s1207 and s1209. The suffixes `scr`/`eff`
are names in the archive; what they mean (scenery vs effect/enemy collision) is **not determined**, a live test (walk the player into an
`h_scr`-only wall) would settle it, which this ticket forbids. Both resources are decoded, gridded and listed.

Observed values of the not-determined triangle words (`h_scr` s1203 / `h_eff` s1203 / s1208): +0x12 takes 14 / 12 / 11 distinct values (1..10 mostly; `10` covers 1,652 of 1,897 in s1203 `h_scr`) - possibly a surface/material id, **not determined**;
+0x14, +0x16 are 0 in all triangles checked; +0x18 takes 16 values (514, 1026, 2, 516, 512, 513 ...: bit flags); +0x1a takes 0, 1, 2, 4; +0x1c takes 45 values (multiples of 4) in `h_eff` and 0 in `h_scr`;
+0x1e is 0 or 0x1000 in `h_eff` and 0 in `h_scr`. Reading them as materials, slopes or "player vs enemy" would be a guess; a table of surface ids against what the game does on them would settle it.

Group records are the key trap: triangle vertex ids restart at 0 in each group (s1203 `h_scr`: groups of 995, 752 and 150 triangles with 638, 534, 126 vertices); without the group's `vert_start` only the first group agrees with its normals.

## Axes, units and frame
* **Up axis is y.** Evidence: floor triangles (stored `ny >= 0.5`) lie under all RAM bonus positions, and RAM y minus the nearest floor y has a median near 130 in every stage (below). RAM and SBC share handedness: the stored normal equals the (v1-v0) x (v2-v0) normal computed from the same vertices in x,y,z order.
* **Units are centimetres, as read (no scale).** Evidence: RAM bonus y minus SBC floor y has a **median between 126.9 and 133.8 in all ten stages** (`h_eff`; exactly 130.0 (+-0.5) for 30 of 94 points, up to 7 of 9-11 in Rail Yard and Requiem for War; a ~1.30 m pick-up hover offset, consistent with the bot's `HEAD_H = 160` cm player height in `re6_switch.py` and `radius_cm` fields of `re6_bomb_blasts.json`). Whether 1 unit is exactly 1 cm in the SBC is not determined by any one number; the match of x,z in the next paragraph (units must agree to land in a floor cell) settles x,z at scale 1.
* **Same origin as the bot's RAM positions.** The bot's recorded positions are the learned stage books (`gbox-data/mercs/learned/01002A000CD48000/stages/s121N.json`, `bonuses`: RAM `pos` of each bonus, written by `re6_switch._stage_book`; this repository's `re6-parity.md` states the book `s121N` equals the archive `s120N`). They are **bonus** positions, not the player's. All 94 of the ten stages' recorded bonus points have an `h_eff` floor triangle under their x,z, and the nearest floor is below them by about 130 cm (median).
* The cross-stage matrix at the end shows the frame is the stage's own: a stage's bonuses only hit its own `h_eff` floor at the 130 cm offset (off-diagonal 0.0 except five cells at 0.07 .. 0.18).
* The player's own y offset above the floor (foot offset) is **not determined** (no player-position samples with a known floor were available; one sample on a known floor per stage would settle it).
* `s121N` book keys use the NO MERCY archive names while the stage table in the ticket uses `s120N`; the equality is taken from `re6-parity.md`, and re-confirmed here only by the cross-stage matrix.

## The grid and the walls
Per stage and per resource (json `stages[].resources.h_scr|h_eff.walk_grid`): origin = floor-snapped min x,z of all vertices of the resource (cm); **25 cm cells** (250 mm); row 0 is the smallest z, column 0 the smallest x; row r, column c
covers x = origin_x + 25c .. +25(c+1), z = origin_z + 25r .. +25(r+1). A cell is `.` if its centre lies under an SBC triangle with stored normal `ny >= 0.5` (floor or a slope up to 60 degrees); `#` if a wall segment crosses a cell that has floor (the segment is
sampled every 6.25 cm) or the cell centre lies under a wall triangle with no floor; else a space. All storeys are merged (a 2D grid). **Wall segments** (`wall_segments_cm_x0_z0_x1_z1`): triangles with `|ny| < 0.5` (steeper than 60 degrees from level) and vertical extent
(max y - min y) **> 100 cm**, each projected to one 2D segment along its horizontal tangent (through the centroid, spanning the extreme vertex projections), rounded to integer cm, duplicates removed; the list is sorted. Ceilings (`ny <= -0.5`) are neither floor nor wall here. `floor cells` in the table counts every cell whose centre is under a floor triangle, **including** those drawn `#`; `blocked cells` counts the `#` characters.
**Run-length coding in the json:** `rows_rle[r]` is a string of tokens `<char><count>` with char `.`, `#` or `s` (space), e.g. `s120.40#3s5` = 120 spaces, 40 floor cells, 3 wall cells, 5 spaces. Rule thresholds are the ticket's; they are method choices, not game data.
Some resources contain far-away triangles (e.g. s1202 `h_eff` spans x -74,842 .. 75,952), so the full-extent grids are large; run-length coding keeps the json at about 2.6 MB. The ASCII renderings below show only the core.

The ASCII rendering: window = the 2nd..98th percentile of non-empty cells, widened to contain every RAM bonus plus 5 m; one character is a k x k block of cells (k printed): `#` if at least a quarter of the block's cells are `#`, else `.` if at least half have floor, else a space; `B` marks a RAM bonus position. Row 0 (top) is the smallest z.
