# Extraction failures become engineering work

Requests #2387 and #2388 ask for local engineering when model extraction fails. Terminal `characters collect` and `characters extract` results now retain an actionable Hermes inbox task when extraction fails, is unsupported, or reports failed/unverified roster entries. A partial **coverage** declaration with a verified subset alone does not manufacture a failure. Intentional cancellations, active jobs, successful extraction, and a picture-point miss do not create work.

The observer reads the stored job and matching accepted receipt. Job, worker, tool, canonical input hash and output hash must agree. The task links the exact receipt and failed entry rows; the full job output remains authoritative when the bounded summary omits rows. Catalog paths describe the selected catalog item, **not verified source bytes**. A worker-reported source SHA is labeled as such, or remains unknown. The engineer must establish the owned source hash before analysis.

Requests group by catalog selection, reported source hash, operation and model/picture selection. Each accepted job has its own durable occurrence record. The request, occurrence, grouping index and audit event commit in one transaction. A repeated delivery is idempotent. A repeated failure joins an active matching task; closed or blocked tasks are preserved and a later failure gets a new task. A single-model extraction's existing gap request is reused only when its source, game and exact job link verify. Parent request links are preserved; the parent is never marked complete.

The normal Hermes work queue handles this work with its existing configured provider, intake and resource policy. No provider, device or completion credit is inferred. The task explicitly asks for source-access diagnosis followed by REA/Ghidra/native-reader engineering, focused tests, independent native asset validation and a same-selection extraction after integration. It is offline work: no game launch, capture, pause/stop, memory/save mutation or replacement. These tasks therefore do not require an emulator admission slot.

The result hook runs after the terminal job receipt commits. If escalation fails, the accepted worker result remains accepted and the error is audited; an exact duplicate result delivery retries this idempotent observer. An explicit reviewed maintenance replay can call `extraction_failures.observe(store, exact_job_id, redact=...)` on a retained matching receipt. There is no blanket historical replay or mass status update.

Acceptance of this automation is separate from the generated engineering task. The infrastructure requests are not closed until the deployed live result path creates the correct task and the configured controller recognizes it. Creating that task does not prove that the missing native reader, any replacement, or the game-specific request is complete.
