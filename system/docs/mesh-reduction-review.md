# Mesh reduction review

Open **Jobs → Review mesh**, or **Compare / report mesh** on a fitting row. Choose the model, orbit or zoom the
linked before/after views, and expand **Why was reduction needed?** for the reported allocation measurements.
**Mark problems on this view** freezes both canvases for numbered boxes/arrows, notes and optional reference
images. A plain note is also supported. The original-mesh preference is checked by default.

Before is the fitted mesh immediately before reduction, so it may already reflect retargeting and proportion
adjustments. The pair contains every saved triangle. It is separate from the sampled, 3,000-triangle progress illustration.
Colours distinguish geometry; these views do not certify native textures, animation, collisions or gameplay.
Fitting files remain bounded to 8 MB each and 256 MB per job. Oversized or expired pairs are unavailable rather
than silently sampled. Old jobs without a pair still accept notes and explicitly say that no exact comparison
was saved.

Soul Calibur II records the surviving decimator faces and moved positions, instead of incorrectly displaying
the original faces under the decimation stage. Its measurements distinguish the configured triangle limit,
vertex-index limit, first attempted allocation and native VMG byte budget. DOA2 records the best allocation
found during refinement, which may differ from the last attempted candidate. Shared Ninja and FF7 fits also
retain comparison pairs and report their configured budgets. A configured triangle cap is a writer policy;
it is not evidence that the original mesh was measured against a hard engine limit.

Submitted reviews retain the original/marked screenshots and both GLB geometry artifacts before temporary job
files expire. Reports enter the existing investigation flow and durable build feedback. Subsequent character
builds for that game must acknowledge the new report revision. Acknowledging feedback does not verify a fix.
The source job, donor, target slot, original-mesh preference and measurements remain attached to the report.

Opening, orbiting, annotating and reporting do not send emulator input, save a running game, launch a build,
or overwrite a source model. New pairs are recorded by supported writers; a report cannot reconstruct a pair
that an older build never saved.
